# ترب بلیت — Torob Tickets

**مقایسهٔ هوشمند قیمت بلیت هواپیما** — یک محصول نمایشی برای چالش مهندسی محصول هوش مصنوعی ترب.

ترب بلیت یک **قیمت‌یاب** است، نه فروشندهٔ بلیت. کاربر فقط مبدأ و مقصد را می‌زند؛ سایت همهٔ پروازهای آن مسیر را در هشت روز پیشِ رو نشان می‌دهد و **زیر هر پرواز** می‌گوید کدام سایتِ فروشنده با چه قیمتی و با چه ظرفیتی همان پرواز را می‌فروشد و ارزان‌ترین را پیشنهاد می‌دهد.

- **یک پرواز = یک کارت** (ایرلاین + شمارهٔ پرواز + روز حرکت به وقت مبدأ + مسیر).
- **نوار تاریخ**: امروز تا امروز+۷، هر چیپ با ارزان‌ترین قیمت همان روز.
- **ظرفیت** کنار قیمت، با هشدار «کم» و کنار گذاشتن فروشنده‌ای که به تعداد مسافران صندلی ندارد.
- هوش مصنوعی فقط «فهم درخواست» و «بازنویسی توضیح» را بر عهده دارد؛ انتخاب ارزان‌ترین، ظرفیت و رتبه‌بندی کاملاً قطعی و تست‌شده است (`selectCheapestOffer`).

> ⚠️ حالت پیش‌فرض هنوز **دادهٔ نمونه** است و در رابط کاربری هم صریح اعلام می‌شود.
>
> از این نسخه، مسیر **دادهٔ واقعی** هم وجود دارد: صفحهٔ `/live` و APIهای `/api/live/*`، متصل به **سپهر۳۶۰** (صفحهٔ عمومی نتایج) و **Amadeus Self-Service** (API رسمی). این مسیر فقط با `TOROB_SEARCH_MODE=live` فعال می‌شود، برای تاریخچهٔ قیمت به PostgreSQL نیاز دارد و هرگز دادهٔ نمونه را به‌جای واقعی نشان نمی‌دهد. جزئیات: [`docs/PROVIDERS.md`](docs/PROVIDERS.md) و [`docs/COMPLIANCE.md`](docs/COMPLIANCE.md).

## اجرا در ۳۰ ثانیه

```bash
npm install
npm run dev          # http://localhost:3000
```

```bash
npm run typecheck    # tsc --noEmit (strict)
```

**صداقت دربارهٔ کش و rate-limit:** `TtlCache` و token-bucketِ منابع و `rate-limit` مسیرهای LLM همه **در حافظهٔ همان پروسس** هستند. روی یک سرور تنها درست کار می‌کنند؛ روی چند نمونه/serverless هر نمونه پنجرهٔ خودش را دارد و کش مشترک وجود ندارد. برای نسخهٔ چندنمونه‌ای به Redis نیاز است که آگاهانه وارد این پروژه نشده (قید معماری مونولیت). این محدودیت روی صفحهٔ `/live` هم دیده می‌شود.

**قرارداد ساختار:** هر چیزی که فقط در یک مسیر استفاده می‌شود، در `_components` همان مسیر است. هر چیزی که بین صفحه‌ها مشترک است در `components/ui`. منطق دامنه هیچ‌وقت داخل `app/` نوشته نمی‌شود.


### خط لولهٔ جستجو

```
POST/GET query
   → adapter.search()  ×۴ (موازی، تایم‌اوت ۲.۵s، خطا = فقط همان منبع خراب)
   → adapter.normalize()  (فرمت خودش → FlightOffer؛ دادهٔ نامعتبر کنار گذاشته و گزارش می‌شود)
   → dedupe.groupOffers()  (یک پرواز فیزیکی = یک گروه، چند نرخ)
   → selectCheapestOffer() (واجد شرایط: قیمت قابل مقایسه، تازه، همان کابین، صندلی ≥ مسافر)
   → rankInputs(fromGroup) (امتیاز قطعی روی *پرواز*، با تعداد واقعی فروشنده‌ها)
   → sortFlights()         (ارزان‌ترین/زودترین/سریع‌ترین/بهترین؛ «تکمیل ظرفیت» آخر)
   → صفحهٔ نتایج / API
```

هیچ‌کدام از مراحل جستجو، dedupe و رتبه‌بندی از هویت ارائه‌دهنده باخبر نیست؛ افزودن منبع جدید (یا **قطار**) فقط یک adapter و یک خط در registry است.

### افزودن ارائه‌دهندهٔ جدید

```ts
export const myAdapter: ProviderAdapter<MyRawOffer> = {
  id: "my-ota",
  name: "آژانس من",
  mode: "demo",
  description: "…",
  quotedCurrency: "IRT",
  async search(query) { /* … */ },
  normalize(raw) { /* از assembleOffer استفاده کنید */ },
};
```

`assembleOffer` مرکزی است: تبدیل ارز، محاسبهٔ مجدد مدت از تایم‌لاین، استخراج تعداد توقف از segmentها، ثبت هشدارها (نبود بار، تبدیل ارز، فرض منطقهٔ زمانی) و ساخت `groupKey`.

### مدل دادهٔ نرمال‌شده

`FlightOffer` شامل: ارائه‌دهنده، ایرلاین، شماره پرواز، مبدأ/مقصد، زمان‌های UTC (+ زمان محلی برای نمایش)، مدت، توقف، segmentها، قیمت اصلی + قیمت تومانی، بار، استرداد، کلاس، لینک، زمان به‌روزرسانی منبع و `warnings[]`.

## چند تصمیم مهم

**۱. اعتماد نکردن به دادهٔ ارائه‌دهنده**
مدت سفر از تایم‌لاین segmentها دوباره حساب می‌شود (فلایتیو عمداً عدد اشتباه می‌دهد)، تعداد توقف از تعداد segmentها (نه از رشته‌های `"direct"`/`"۲ توقف"`)، و قیمت ریالی/یورویی با جدول نرخ نمونه به تومان تبدیل و با هشدار `price-converted` علامت می‌خورد.

**۲. دادهٔ نامشخص هرگز حدس زده نمی‌شود**
اگر ارائه‌دهنده بار یا استرداد را اعلام نکند، مقدار `null` می‌ماند، در UI «نامشخص» نمایش داده می‌شود و هوش مصنوعی اجازهٔ ادعا درباره‌اش را ندارد.

**۳. حذف تکراری محافظه‌کارانه**
کلید یکسان = ایرلاین + شمارهٔ پرواز یکسان‌سازی‌شده + **روز حرکت به وقت مبدأ** + مسیر. قاعدهٔ دقیق:

- دو نرخ با شمارهٔ پرواز یکسان همیشه یکی هستند.
- نرخِ **بدون شماره** هرگز به یک پرواز شماره‌دارِ فروشندهٔ دیگر نمی‌چسبد (ادعای اثبات‌نشده).
- نرخِ بدون شماره فقط با نرخِ بدون شمارهٔ همان ایرلاین و در فاصلهٔ حداکثر **۵ دقیقه** یکی می‌شود؛ کارت آن را «شناسایی بر پایهٔ ساعت حرکت» برچسب می‌زند.
- همان فروشنده اگر یک بار با شماره و یک بار بدون شماره همان لحظه را منتشر کند، دو ردیف نمی‌شود.

تست‌ها موارد منفی (قیمت مشابه، پرواز متفاوت، دو روز مختلف) را پوشش می‌دهند.

**۴. رتبه‌بندی قطعی، هوش مصنوعی فقط توضیح‌دهنده**
`score = Σ wᵢ · sᵢ` با `sᵢ ∈ [0,1]`؛ زیرامتیاز قیمت/مدت نسبتی است (`بهترین / مقدار`) تا یک پرواز بیزینس گران، کل بازه را فشرده نکند. وزن‌ها از intent می‌آیند و نرمال می‌شوند. محدودیت‌های سخت (توقف، بار، استرداد، بودجه، بازهٔ ساعت) گزینه را حذف نمی‌کنند؛ در بخش «خارج از ترجیحات» با دلیل نمایش داده می‌شوند.

**۵. هوش مصنوعی قابل حذف**
بدون `OPENAI_API_KEY`: پارسر قطعی فارسی/انگلیسی intent را می‌سازد و توضیح‌ها از قالب‌های قطعی می‌آیند. با کلید: مدل فقط می‌تواند بازنویسی کند؛ خروجی باید با Zod معتبر شود و از `checkGrounding` بگذرد (هر عددی که در داده نیست، هر ادعا دربارهٔ فیلد ناشناخته، هر شماره پرواز دیگر → رد و استفاده از قالب). کلید فقط سمت سرور است.

**۶. ماندگاری اختیاری (Postgres محلی، بدون داکر)**
اجرای دمو کاملاً در حافظه است و به دیتابیس نیاز ندارد. اگر `DATABASE_URL` ست شده باشد، هر جستجو به‌صورت best-effort ثبت می‌شود: snapshot پیشنهادهای نرمال‌شده + لاگ جستجو (intent، تعداد نتایج، بهترین پیشنهاد). خطای دیتابیس هیچ‌وقت صفحه را نمی‌شکند و پیام یک‌بار در کنسول لاگ می‌شود.

Postgres خودِ ویندوز کافی است — جزئیات در بخش «اتصال به Postgres روی ویندوز».

**۷. زمان و تاریخ**
همهٔ زمان‌ها به UTC ذخیره می‌شوند؛ زمان محلی هر فرودگاه با `Intl` محاسبه می‌شود (بدون جدول offset دستی، با احتساب DST). تاریخ‌ها در UI شمسی و با ارقام فارسی‌اند؛ تقویم شمسی با الگوریتم حسابی نوشته و با تاریخ‌های مرجع تست شده است (۱ فروردین = ۲۱ مارس).

## اتصال به Postgres روی ویندوز (بدون داکر)

دیتابیس خودتان کافی است؛ هیچ container‌ای لازم نیست.

### ۱) ساخت دیتابیس

با pgAdmin یا `psql`:

```sql
CREATE DATABASE torob_tickets;
```

### ۲) ست کردن `DATABASE_URL`

`DATABASE_URL` باید شامل **نام کاربری، رمز، هاست، پورت و نام دیتابیس** باشد. اگر رمزتان کاراکترهای خاص دارد (`@ : / ? # %`) آن را URL-encode کنید (مثلاً `@` → `%40`).

**PowerShell (فقط برای همان پنجرهٔ ترمینال):**
```powershell
$env:DATABASE_URL="postgresql://postgres:MyPass@localhost:5432/torob_tickets?schema=public"
```

**CMD:**
```cmd
set DATABASE_URL=postgresql://postgres:MyPass@localhost:5432/torob_tickets?schema=public
```

**یا دائمی‌تر:** یک فایل `.env` در ریشهٔ پروژه بسازید (در `.gitignore` هست، کامیت نمی‌شود):
```
DATABASE_URL="postgresql://postgres:MyPass@localhost:5432/torob_tickets?schema=public"
```

> اگر پورت پیش‌فرض را عوض کرده‌اید (مثلاً نصب با EDB معمولاً 5432 است)، همان پورت را در URL بگذارید. سرویس `postgresql-x64-16` باید در `services.msc` در حال اجرا باشد.

**Prisma 7:** آدرس اتصال دیگر داخل `schema.prisma` نوشته نمی‌شود؛ CLI آن را از `prisma.config.ts` می‌خواند (که خودش `.env` را بار می‌کند) و اپلیکیشن در زمان اجرا با درایور `@prisma/adapter-pg` وصل می‌شود.

### ۳) ساخت جدول‌ها و دادهٔ نمونه

```powershell
npm run db:generate
npm run db:push       # ساخت جدول‌ها از schema.prisma
npm run db:seed       # پر کردن با خروجی واقعی خط لولهٔ جستجو
npm run db:studio     # (اختیاری) مرور داده‌ها در مرورگر
```

### ۴) اجرا

```powershell
npm run dev
```

از این به بعد هر جستجو در `search_logs` و `offer_snapshots` ثبت می‌شود. برای بررسی سریع:

```sql
SELECT origin_code, destination_code, result_count, source, created_at
FROM search_logs ORDER BY created_at DESC LIMIT 10;
```

### اگر خطا گرفتید

| خطا | علت | راه‌حل |
|---|---|---|
| `Can't reach database server` | سرویس Postgres خاموش است یا پورت/هاست غلط است | سرویس را در `services.msc` روشن کنید، `localhost:5432` را چک کنید |
| `password authentication failed` | رمز یا نام کاربری غلط | با pgAdmin همان رمز را تست کنید؛ کاراکترهای خاص را URL-encode کنید |
| `database "torob_tickets" does not exist` | دیتابیس ساخته نشده | `CREATE DATABASE torob_tickets;` |
| `@prisma/client did not initialize yet` | `prisma generate` اجرا نشده | `npm run db:generate` |
| `Cannot resolve environment variable: DATABASE_URL` | CLI به URL نیاز دارد (v7) | فایل `.env` بسازید یا متغیر را در همان ترمینال ست کنید |
| `کلاینت دیتابیس ساخته نشده است` | `src/generated/prisma` وجود ندارد | `npm run db:generate` |
| صفحه با خطای دیتابیس بالا نمی‌آید | نباید رخ دهد — نوشتن best-effort است | `DATABASE_URL` را بردارید؛ اپ بدون دیتابیس هم کامل کار می‌کند |

> **نکته:** بدون `DATABASE_URL` هیچ‌چیز خراب نمی‌شود؛ دمو کاملاً در حافظه اجرا می‌شود. ماندگاری یک قابلیت اضافه است، نه پیش‌نیاز.

## مسیر دادهٔ واقعی (Live)

حالت پیش‌فرض `demo` است. برای دادهٔ واقعی:

```bash
# ۱) دیتابیس (اجباری برای تاریخچهٔ قیمت)
CREATE DATABASE torob_tickets;
# PowerShell:
$env:DATABASE_URL="postgresql://postgres:PASS@localhost:5432/torob_tickets?schema=public"
npm run db:generate ; npm run db:push ; npm run db:seed

# ۲) حالت واقعی
$env:TOROB_SEARCH_MODE="live"

# ۳) بررسی دستی اتصال (این دستورها به سایت واقعی وصل می‌شوند؛ در CI اجرا نمی‌شوند)
npm run provider:check sepehr360
npm run search:live THR MHD 2026-11-20
npm run db:doctor
npm run db:history -- THR MHD 2026-11-20
```

سپس `/live` (و `/api/live/search?origin=THR&destination=MHD&date=…&mode=live`) در دسترس است.

**آنچه باید بدانید:**

- **سپهر۳۶۰** یک صفحهٔ عمومی نتایج است. شمارهٔ پرواز، بار مجاز، شرایط استرداد و موجودی را
  اعلام نمی‌کند؛ این فیلدها `null`/«نامشخص» می‌مانند و در کارت هر نرخ دیده می‌شوند. تنها لینک
  ممکن، صفحهٔ جست‌وجوی همان مسیر است (لینک اختصاصی نرخ وجود ندارد).
- **Amadeus** یک API رسمی و مستقل است، اما جانشین قیمت بازار ایران نیست. قیمت‌ها ارزی‌اند و
  **بدون نرخ تبدیل ساختگی** به تومان، قابل مقایسه با نرخ‌های ایرانی نیستند (در رتبه‌بندی تومانی و
  نمودار قیمت وارد نمی‌شوند). دادهٔ محیط تست، نمونهٔ کش‌شده است و همان‌طور برچسب می‌خورد.
- **تاریخچهٔ قیمت** از اولین مشاهدهٔ واقعی شروع می‌شود. هیچ نقطه‌ای برای گذشته ساخته نمی‌شود.
- **یک منبع خراب بقیه را متوقف نمی‌کند**: هر منبع گزارش جداگانه (`ProviderRunReport`) با کد خطا،
  تأخیر و تعداد رکورد دارد و در `/api/health` هم دیده می‌شود.

بررسی انطباق (robots.txt، ToS، محدودیت نرخ، و اینکه چرا Alibaba حذف شد) در
[`docs/COMPLIANCE.md`](docs/COMPLIANCE.md) آمده است.

## محدودیت‌های شناخته‌شده

- **دادهٔ نمونه**: افزایش قیمت با نزدیک‌شدن تاریخ، جدول پرواز هفتگی، نرخ ارز ثابت — همه ساختگی و مستند.
- **اتصال واقعی در این محیط آزمایش نشده**: sandbox به سایت‌های هدف دسترسی شبکه ندارد؛ صحت
  اتصال باید با `npm run provider:check` روی دستگاه خودتان تأیید شود. تست‌های واحد فقط با
  fixture کار می‌کنند و هیچ‌گاه به سایت واقعی وصل نمی‌شوند.
- **سپهر۳۶۰** شمارهٔ پرواز و بار/استرداد نمی‌دهد → این نرخ‌ها هرگز با نرخ‌های Amadeus ادغام
  نمی‌شوند و «موجودی» برایشان اعلام نمی‌شود.
- **پرواز رفت‌وبرگشت**: فرم نوع سفر و تاریخ برگشت را می‌پذیرد، اما نتایج فعلاً فقط پای رفت را نشان می‌دهند.
- **بلیت واقعی**: لینک‌ها به دامنهٔ نمونه می‌روند و خرید انجام نمی‌شود.
- **قطار**: مدل دامنه و لایهٔ ارائه‌دهنده، مستقل از وسیلهٔ سفر طراحی شده‌اند اما پیاده‌سازی نشده‌اند.
- **Playwright**: اجرای خودکار نتیجه به نصب مرورگر نیاز دارد؛ در محیط محدود، پوشش همان جریان با `journey.dom.test.tsx` انجام می‌شود.
- **Prisma**: تولید کلاینت به دسترسی شبکه نیاز دارد؛ در نبود آن، لایهٔ ماندگاری غیرفعال می‌ماند و دمو اثری نمی‌بیند.
